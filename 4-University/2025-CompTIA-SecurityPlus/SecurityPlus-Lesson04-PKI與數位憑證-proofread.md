## 🎯 身分驗證基石：憑證私鑰、OTP 一次性密碼與社交工程防禦

**【授課講師】**：自然人憑證就像你個人的數位私章。政府機關或戶政單位手上絕不會保有你的私鑰（私章），因此一旦自然人憑證遺失了該怎麼辦？唯一做法就是立即申請掛失廢止，並重新產製一組全新的金鑰對與憑證。

第二種常見的身分驗證機制是 **OTP（One-Time Password，一次性密碼）**。當使用者忘記密碼時，系統會動態生成一組具有時效限制的暫時性密碼發送至信箱，要求使用者登入後立即強制變更密碼。

此外，在現代快速身分驗證與雙因子驗證（2FA / MFA）架構中，採用通用第二要素（U2F / FIDO）標準。如果驗證流程遇到阻礙，向官方客服申請身分救援時，客服人員會嚴格詢問安全提問與輔助驗證資訊；若回答錯誤，客服絕對不會通融放行。

身分驗證可區分為：
- **硬性身分驗證（實體 Token / 硬體金鑰）**：如自然人憑證智慧卡、FIDO 實體安全金鑰等，安全性最高；
- **軟性身分驗證（通訊管道驗證）**：透過 Email、簡訊 SMS 或電話通知發送驗證碼。

軟性驗證（特別是簡訊 SMS）存在嚴重的攔截與社交工程風險！
例如常見的詐騙手法：歹徒假冒 Facebook 或各大平台客服，謊稱系統檢測到異常要求重設密碼；使用者收到官方寄送的重設授權碼簡訊後，歹徒透過通話誘騙使用者交出該組授權碼。一旦歹徒取得授權碼，便能瞬間奪取該帳號的管理權限，將原本綁定的信箱與手機全數置換踢除，進而假冒受害者身分對通訊錄好友發動借錢與釣魚詐騙。

早期社群平台安全機制不周，若有人申請將帳號綁定新信箱，系統若僅單方面向舊信箱發信通知、且在特定時限內未獲拒絕即預設核准變更，極易遭駭客利用此漏洞進行惡意盜帳號。現代成熟的防禦機制全面要求 **多因子驗證（MFA）**，強制綁定手機 Authenticator App（每 30 秒動態更新 6 位數 TOTP）或 FIDO 生物辨識，徹底阻斷攔截風險。

## 🧬 多因子身份驗證（MFA）與生物特徵識別（Biometrics）

**【授課講師】**：在進階雲端環境中，已逐步邁向 **無密碼身分驗證（Passwordless Authentication）** 架構。傳統靜態密碼極易因人為疏忽、撞庫攻擊或記憶混淆而外洩。

例如在 Amazon AWS 雲端維運中，管理員登入 EC2 Linux 主機時，預設完全不使用帳號密碼，而是使用非對稱加密產生的 **金鑰對（Key Pair，`.pem` 檔案）**。管理員在本地端 SSH 軟體中載入私鑰，與雲端實例上的公開金鑰完成公鑰基礎設施（PKI）非對稱交握驗證，直接建立安全 SSH 加密通道。這從根本上消除了弱密碼與字典暴力破解的安全隱憂。

在嚴格的驗證情境中，MFA 會整合多種驗證維度：
1. **Something you know（所知之事）**：密碼、PIN 碼；
2. **Something you have（所持之物）**：智慧卡、硬體 Token、手機 Authenticator；
3. **Something you are（所是之特徵）**：指紋、人臉、虹膜等生物辨識（Biometrics）。

各項要素相互佐證建立高強度的信任鏈，確保存取操作合法合規。

## 🛡️ 存取控制模型剖析：DAC、MAC、RBAC 與 ABAC

**【授課講師】**：接下來探討作業系統與雲端資源的存取控制模型（Access Control Models）：

當我們使用 Windows、Linux 或 macOS 等主流作業系統時，底層的帳號權限管理機制主要涵蓋以下典範：

1. **DAC（Discretionary Access Control，自主存取控制）**：
   - 這是個人電腦與通用商用作業系統（Windows / Linux 預設環境）最普遍的機制。
   - **核心哲學：以「資源擁有者（Owner）」為中心**。檔案或目錄的建立者即為該物件的擁有者，擁有者有權「自主決定」要將讀取（Read）、寫入（Write）、執行（Execute）等權限開放給哪些其他使用者。
   - 在 Linux/Unix 中有經典的 `rwx` 權限；在 Windows 中則依賴 **ACL（Access Control List，存取控制清單）** 記錄每位使用者對該檔案的權限。
   - 附帶一提，Linux 系統上運行 Windows 程式的知名相容層軟體叫做 **Wine**（Wine Is Not an Emulator，紅酒之意），正是利用系統呼叫轉譯來模擬執行 Windows 應用程式。

2. **MAC（Mandatory Access Control，強制存取控制）**：
   - 廣泛應用於國防軍事機密系統與高度受規管環境（如 SELinux）。
   - **核心哲學：中央極權管理，個人無權更動**。資源擁有者完全不能自行決定權限！
   - 系統依據預先制定的安全政策，為所有主體（Subject，使用者/程序）標註安全許可等級（Security Clearance，如機密、極機密），為所有客體（Object，檔案/資源）**貼上敏感度標籤（Sensitivity Labels）**。只有當使用者的許可等級大於或等於檔案標籤時，系統才允許存取，絕不容許私下分享。

3. **RBAC（Role-Based Access Control，以角色為基礎的存取控制）**：
   - 大型企業與雲端平台（AWS IAM、Azure RBAC）的絕對主流標準！
   - **痛點比喻**：如果公司有 100 位員工要存取檔案，若採用傳統 DAC 為每個人個別設定 ACL 清單，管理員要維護 100 筆設定，費時且極易出錯；就像公司要辦尾牙宴會通知 100 人，秘書不可能逐一打 100 通電話，而是通知各部門主管（Group Leader）由各組織轉發。
   - **運作機制**：管理員不將權限直接綁定在「個人帳號」上，而是先定義「**角色（Role，如財務審核員、系統維運員）**」，將存取權限賦予角色；再將員工帳號或安全群組（Security Groups）指派加入該角色。員工自動「繼承」該角色的所有權限。當人員離職或職務調動時，僅需調整角色歸屬，全系統權限瞬間自動同步，大幅落實**最小權限原則（Principle of Least Privilege）**。

4. **ABAC（Attribute-Based Access Control，以屬性為基礎的存取控制）**：
   - 最靈活且現代化的動態存取控制模型。
   - 不僅檢查角色，而是綜合評估四大維度的多重屬性：
     - **主體屬性（Subject Attributes）**：使用者的部門、職級、身分認證等級；
     - **客體屬性（Object Attributes）**：檔案機密等級、檔案類型、所屬專案；
     - **環境屬性（Context/Environment Attributes）**：存取時間（是否為上班時間）、連線來源 IP 位址、存取設備是否合規（Device Posture）、地理位置；
     - **動作屬性（Action Attributes）**：讀取、編輯、列印、下載。
   - 只有當即時情境完全滿足預設的布林邏輯規則時，系統才動態授予存取授權，具備細緻的上下文感知能力。

無論是 AWS、Azure 還是底層 Linux、Windows，核心資安概念皆建立在這些存取控制模型之上。大家必須透徹理解其運作邏輯，認證考試中這是核心常考題型。
