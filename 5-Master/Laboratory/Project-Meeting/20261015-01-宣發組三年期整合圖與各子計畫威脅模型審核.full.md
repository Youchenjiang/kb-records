## 🗺️ 宣發組三年期總計畫架構整合圖與威脅模型修訂

**【侑宸】**：好，我們做了一個開會記錄。這次討論主要有三個核心要點：

**【侑宸】**：第一個點是，我們宣發組下禮拜固定要完成的事項有哪些。首先是完成宣發組與子計畫二、子計畫三這三年期的架構整合。我們要在計畫的三個年度之間畫出一張完整的總體架構圖，在下次大會報告的時候先正式呈現出來。

**【指導教授】**：所以第一點的意思是，修改模型是指我們自己的模型，還是每一組都要做到？

**【侑宸】**：每一組都要做到！每一組的「威脅模型（Threat Model）」都要修改並完善他們自己現有的威脅模型架構。這是我們各組必須落實的兩大事項之一。主要三年期計畫就是我們整體三年計畫的技術藍圖。

**【侑宸】**：至於會前會這邊先不用，我們先討論內部大概要準備什麼：在 11 月正式會議之前，總計畫那邊會將計畫大綱的整體內容架構填好，並在正式會議中進行全面匯報。那我們各組要做的，就是將各子計畫要填寫的技術細節與三年期成果指標完整填報上去。這是在管考會議上必須備妥的核心資料。

## ⚔️ 黑箱與白箱滲透之本質辯證：開發者視角 vs 真實攻擊者視角

**【侑宸】**：今天在跨組討論的時候，其他組別的審查代表提出了兩個非常尖銳的關鍵問題：

**【侑宸】**：第一個問題是：**「為什麼堅持要做黑箱滲透測試，而不是直接做白箱原始碼審計？」** 他們質疑黑箱滲透探討與能發現的問題，數量上往往比白箱原始碼掃描還要少；既然白箱能看到全部原始碼，為什麼不直接做白箱就好？

**【侑宸】**：我們今天當場提出的立論差異在於兩點：
1. **白箱原始碼審計（White-box）**：是在擁有 Source Code 的前提下進行。開發者審視代碼時，本能上是站在**「開發者的業務邏輯視角」**，去檢驗程式碼執行出來的功能是否符合原始設計規格。
2. **黑箱滲透測試（Black-box）**：是在完全不知道 Source Code 與後端內部架構的前提下運作。黑箱代表的是**「外部真實攻擊者的視角（Attacker's Perspective）」**。

**【侑宸】**：真實攻擊者不會按照開發者預設的良善路徑點擊。黑箱測試所探索出來的滲透路徑與漏洞利用鏈，往往能突破開發者燈下黑的盲點，挖掘出異常的邏輯跳步、未授權存取與業務邏輯漏洞。

**【指導教授】**：對！今天能夠在會上被問出這個問題非常有價值！因為我們自己在做研究時，常常會陷入「當局者迷」的盲點。別人從外部審查的角度來看，就會直接挑戰我們的核心立論依據。

**【指導教授】**：我們開發這套自動化工具，假設是為了支援開發者在軟體開發生命週期（SDLC）中使用。既然是給開發者使用，開發者明明擁有原始碼，你為什麼一定要堅持使用者視角與黑箱？

**【指導教授】**：你必須在論證上說清楚：直接去看程式碼，跟從外部介面去探測，到底有什麼本質區別？有些邊界問題——例如執行時態的時序競爭（Race Conditions）、跨元件的環境配置錯誤，在靜態白箱程式碼裡面是看不出來的！

**【指導教授】**：更重要的是：**光用文字這樣講是不夠的，必須拿出一個具體的「鐵證案例（Concrete Example）」！** 下次報告時，一定要挑出一個明確的漏洞範例：說明這個漏洞在白箱靜態審查時為何會被忽略，而我們的黑箱動態探索工具是如何一步一步成功抓出來的！只要拿出一個無可辯駁的真實案例，就能徹底說服審查委員！

**【侑宸】**：明白，我們會挑選一個最典型的邏輯越權案例來做對照驗證。

**【侑宸】**：今天被問到的第二個問題是：**「我們的自動化探索為什麼採用 GUI 探索的方式去抓取 API 的各個呼叫路徑？為什麼不直接從白箱文檔中讀取 API 規格？」**

**【侑宸】**：我們現場的回應是：真實攻擊者在面對 Web 與行動系統時，前端 GUI 介面是觸發動態 API 請求的唯一入口。過去國際頂尖安全論文（如 USENIX Security、NDSS），在探討真實漏洞利用時也都是採用黑箱動態 GUI 探索來建構攻擊路徑。這兩個核心問題我們後續都會補上扎實的實證數據來支撐。

## 🧠 大語言模型工具調用 Token 成本優化：引入專用 Judge 評判小模型

**【侑宸】**：接下來匯報我近期在系統架構上推進的一項重要技術突破：**引入專用的 Judge 評判模型（LLM-as-a-Judge）以大幅降低 Token 開銷**。

**【侑宸】**：在目前的系統架構中，當我們的自主代理（Agent）遇到任務時，原本是直接呼叫高階大模型（如 Claude 3.5 Sonnet 或 Opus）。為了讓大模型決定下一步要調用哪一項工具，系統必須載入大量的錯誤歷史日誌與龐大的工具定義清單。

**【侑宸】**：大模型載入這些厚重的上下文後，會輸出一大串冗長的思維鏈（Chain-of-Thought, CoT）推理文字，例如：「經過深思熟慮，考慮到當前日誌報錯，我認為應該調用工具 A，接下來需要執行步驟一二三...」。

**【侑宸】**：這種傳統方式造成兩個致命痛點：
1. **API 成本極為高昂**：高階大模型的輸入與輸出 Token 單價極貴，且反覆輸出長篇 CoT 浪費大量預算。
2. **延遲嚴重**：大模型生成冗長文字大幅拖慢了自動化漏洞探索與代碼修復的吞吐效率。

**【指導教授】**：所以你現在找出的替代方案是什麼？這個 Judge 模型具體是怎麼運作的？

**【侑宸】**：我們引入專用的評判模型（Judge Model），例如基於開源 Llama 微調打造的專用分類小模型。這個 Judge 模型只專注做一件事——**「工具調用與修復策略的極速決策評判」**。

**【侑宸】**：它不需要生成任何廢話思維過程，它的輸出被嚴格限制為三種結構化型態：
1. **機率分佈（Probability / Value）**：輸出一個 0 到 1 之間的正實數，代表成功機率評估。
2. **選項選擇（Choice with Confidence）**：在給定的候選工具清單（A, B, C, D）中直接輸出選定標籤，並附帶信心度數值。
3. **評分機制（Score）**：對當前自動生成的修復補丁或攻擊路徑給予 0 至 10 分的量化評分。

**【指導教授】**：它為什麼能幫你省下那麼多 Token 費用？

**【侑宸】**：關鍵就在於「Token 經濟學的輸入單價與輸出長度」：
- **小模型單價極低**：相比於 Claude Opus 等龐然大物，專用小模型（如 Llama-based Judge）即便載入相同的錯誤日誌，其運算單價只有大模型的幾十分之一。
- **輸出 Token 趨近於零**：大模型輸出一次就是幾百個 Token 的長篇大論；而專用 Judge 模型本質上是一個機率選擇器，輸出僅有短短幾個字元（例如一個選項代號或一個數字評分），輸出 Token 數幾乎為零！

**【侑宸】**：事情在 Judge 評判層就完成了工具選取與路線裁決，完全不需要再呼叫昂貴的大模型反覆輸出冗長思考過程。這能省下大量的 API 預算，並讓我們的自動修復迴圈執行速度提升數倍！

**【指導教授】**：非常好！這個邏輯完全說得通！透過分層架構（Hierarchical Architecture），讓輕量專用小模型處理高頻的工具路由與邊界決策，真正複雜的代碼生成才交給大模型。這不僅大幅降低系統運作成本，更是兼具工程實用性與學術創新價值的優秀亮點！
