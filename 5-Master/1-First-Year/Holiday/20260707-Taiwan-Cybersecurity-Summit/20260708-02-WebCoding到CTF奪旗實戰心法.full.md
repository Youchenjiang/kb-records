# 🎙️ 從 Web Coding 到 CTF 奪旗實戰：AI 輔助開發的陷阱防範與 Git Worktree 隔離工作流

> **【排版與校對說明】**：
> 本文件收錄資安顧問、Baselines 安全程式碼社群發起人 **Miss Tika** 於 InfoSec Taiwan 2026 第二日社群高峰論壇之演講全文逐字稿。
> 講者以自身從苦學 JavaScript 到運用 AI 打造「乙女向帥哥解謎遊戲」的 Side Project 為引子，生動且犀利地揭露一人開發者在高度依賴 AI 程式碼生成時所遭遇的四大核心危機：**需求發散與腦補幻覺、冰山底下的安全漏洞（Bypass 認證、過度過寬 CSP 與權限缺失）、PR 膨脹與髒 Commit 災難、以及過度設計與微服務濫用**。

## 💥 災難的第一版：美工崩壞、遺失存檔與需求失控

**【Miss Tika】**：大家可以看看我的第一版產出長什麼模樣——這畫面跟「帥哥男主角」到底有半毛錢關係？完全沒有！看起來簡直就像是從暗網某個角落偷出來的詭異介面。

我仔細檢討第一版到底炸在哪裡：
1. **語系大亂鬥**：不知道是不是因為我提示詞下了「乙遊（乙女遊戲）」，模型就自己腦補，產出日文與英文胡亂夾雜的介面。
2. **角色設定錯亂**：明明說好是帥哥遊戲，右上角居然冒出一個紅色雙馬尾的病嬌女角色？完全黑人問號！
3. **基礎功能殘缺**：遊戲完全沒有實作任何儲存機制，玩到一半只要重新整理，遊玩紀錄全部蒸發。
4. **審美完全不及格**：玩乙女遊戲最重要的就是立繪要帥、畫面要精緻、情緒價值要拉滿；看到那種慘不忍睹的圖，我身為開發者自己都想立刻關掉視窗！

接下來，我就犯了所有初學者接觸 AI 時都會犯的典型錯誤——我開始無止境地在對話視窗裡跟它盧：
- *「可不可以幫我改一下人物設計？」*
- *「可不可以去素材庫幫我換一下立繪？怎麼還是不對！」*（順帶一提，現場如果有很會畫圖的朋友，歡迎會後聯絡我一起做 Side Project！）
- *「題目感覺不夠吸引人，幫我重新設計題庫！」*
- *「為什麼沒有登入功能跟存檔機制？」*

在這裡我撞上了**第一個核心盲點：在開發者自己都還沒釐清產品定位與核心規格時，你根本不可能對 AI 下出精準的需定義！**

很多人會事後諸葛地說：「那你一開始就該把需求拆分好啊！」但現實是一人開發的 Side Project，你往往連產品最後會長成什麼樣都還在摸索，你怎麼可能在一開始就寫出完美的 PRD（產品需求文件）？

## 🧊 冰山底下的資安危機：API 裸奔、越權存取與過度過寬 CSP

**【Miss Tika】**：後來我耐著性子跟 AI 來回磨合，終於產出了一個看似像樣的版本：有可攻略的角色、每個角色對應不同的題目類型（例如 Web 題、Pwn 題、密碼學或實體安全題）。

我在 Demo 時故意模擬一個完全不懂規則、連續答錯題目的糟糕使用者體驗。照理說，如果玩家一直答錯，系統應該判定失敗、無法看到隱藏結局對吧？

但驚人的事情發生了！當我稍微打開瀏覽器的開發者工具（F12）檢查底層程式碼時，我整個人愣住了。

畫面上看起來很漂亮、UI 很完整，但在這座冰山底下，AI 寫出來的程式碼塞滿了不可思議的安全漏洞：
1. **邏輯繞過（Business Logic Bypass）**：前端雖然擋住未通關的使用者，但底層 API 根本沒有驗證遊戲狀態！任何人不需要回答任何題目，只要自己對後端發送一個 API Request，就能直接取得通關 Flag 與大結局！
2. **完全裸奔的 API 與越權存取（BOLA / IDOR）**：API 完全沒有做 Session 與角色權限管控（Authorization），任何人都能呼叫管理端介面。
3. **過度放寬且危險的 CSP（Content Security Policy）**：AI 為了讓內嵌腳本能動，在 HTTP Header 裡設定了極其糟糕的 CSP，甚至直接開啟 `unsafe-inline` 與 `unsafe-eval`，把 XSS 防護門戶大開。
4. **過度簡化且脆弱的認證機制**：密碼處理與 Token 機制漏洞百出。
5. **程式碼過度設計（Over-engineering）與防禦失靈**：明明不需要的地方塞滿了層層無意義的 `try-catch` 和冗長的 `if-else`，真正關鍵的邊界條件卻完全漏掉。

這是我踩到的第二個巨大教訓：**AI 產出的前端畫面可能光鮮亮麗，但冰山底下埋藏的卻是千瘡百孔的資安技術債！**

## 🌪️ 版本控管浩劫：一人開發的「百變怪 PR」與髒 Commit 災難

**【Miss Tika】**：當我想把這個 Side Project 擴大、準備推上 GitHub Remote Repository，甚至想邀請社群好友一起協作時，我遇到了第三個災難。

因為 AI 產出程式碼的速度「又快又猛」，我常常跟它聊了兩個小時，它就一口氣改了幾十個檔案。這時候如果直接打包 Commit 推上去，整條 Git 歷程會變得極度骯髒與混亂：
- 同一個 Commit 裡，同時包含了「A 功能（角色立繪更新）」、「B 功能（API 認證）」、「C 功能（題庫重構）」；
- Commit Message 混亂不堪，完全看不出修改目的；
- 建立出來的 Pull Request（PR）變成一張巨大的「百變怪 PR」，裡面的 File Changes 高達幾十個，跨越不同模組。

我現場請教大家：如果你在團隊裡看到這樣的 PR，你會給它打幾分？

我自己直接打「0 分」！

如果未來線上環境爆出 Bug，接手維護的工程師順著 Git Blame 追到這張 PR，他根本不可能知道當初到底為什麼要改這些程式碼，更無法評估修改帶來的副作用，最終演變成整個專案無法 Deploy、無人敢碰的技術死局。

除了 PR 混亂之外，AI 輔助開發還有很多常見的地雷：
- **工具選擇錯誤**：明明需要永久儲存的資料，AI 居然自作主張拿 Redis Cache 來當長期儲存庫；
- **微服務過度濫用**：一個簡單的個人小專案，AI 沒有任何合理架構理由，就把它硬拆成十幾個獨立微服務，大幅增加通訊延遲與維運複雜度；
- **模型幻覺（Hallucination）**：AI 信誓旦旦地回報：「我已經幫你加上了防禦機制，防止危險的檔案刪除操作」，但實際上打開底層原始碼一看，根本什麼防護都沒寫！

## 🛠️ 解法一：反向提問對齊法（Alignment Prompts）與多角色規格架構

**【Miss Tika】**：面對上述痛點，我們該如何系統化解決？

首先是「需求混亂」的問題。一人開發者最常陷入的盲點，是把自己同時當成產品經理、市場調研、系統架構師與研發工程師，腦袋塞滿雜訊。

解法核心在於：**階段拆分與職責分離**。

我借鏡了傳統軟體工程與 BMF 流程的規劃階段理念，將開發切分為明確角色：
1. **Analyst（分析師）**：負責調研與可行性評估；
2. **PM（產品經理）**：負責收斂邊界，精確定義需求；
3. **Architect（架構師）**：負責依據需求繪製系統藍圖與資料結構；
4. **Developer（研發工程師）**：最後才依據架構藍圖撰寫程式碼。

在實務上，最有效的 Prompt 心法叫做**「反向提問對齊法」**：
> **「千萬不要一開始就要求 AI 提供程式碼或解決方案！而是要求 AI 持續向你提問，直到你無法回答為止！」**

當你給定一個初步想法時，讓 AI 擔任需求審查員：
- 條列它目前已理解的需求邊界；
- 列出規格中模稜兩可、衝突或缺漏的部分；
- 逐一向開發者拋出確認問題，引導你補齊邏輯盲點。

當你發現某個問題你回答不出來時，那個盲點就是你專案未來的潛在風險！透過這個來回辯證過程，產出一份明確的規格藍圖（Spec）與風險評估報告。

在工具選擇上，做前期規格規劃與大脈絡對齊時，我個人非常推薦使用具備超大 Context Window 的模型（如 Gemini），能夠一次吃下完整專案背景而不遺忘。

另外，請務必養成一個「肌肉記憶」：**定期清理舊規格文件！** 如果你讓過期、作廢的 Spec 散落在 Codebase 裡，AI 下次檢索上下文時很可能會把舊的錯誤規格混進新邏輯中，造成災難性的混亂。

## 🛡️ 解法二：人工審查關鍵節點（Human-in-the-Loop）與安全防護梯隊

**【Miss Tika】**：第二個核心議題是安全防禦。

常有開發者問我：「既然 AI 寫 code 這麼強，我們是不是可以直接跳過 Code Review，直接部署上線？」

我必須非常嚴肅地強調：**AI 產出的程式碼，必須遵守與人類工程師完全相同、甚至更嚴格的安全規範！人工審查（Human-in-the-loop）是絕對不可省略的最後一道防線！出事背鍋的永遠是人，絕對不是 AI！**

我們可以在本機與 CI/CD 流程中建立多層防禦梯隊：
1. **本機 IDE 即時輔助**：安裝 SonarQube、Snyk 等外掛，在代碼生成的第一時間抓出常見靜態漏洞；
2. **預先推送安全掃描**：在 Git Push 之前，強制執行 SAST/SCA 工具（如 Semgrep、GitGuardian）掃描敏感金鑰與注入漏洞；
3. **安全代理人（Security Reviewer Agent）**：設計專門的資安 Review Prompt / Skill，在合併代碼前以攻擊者視角檢視變更。

此外，人工審查必須精準聚焦在以下**「高危關鍵節點」**：
- **破壞性檔案操作**：任何涉及 `rm -rf`、批次刪除或資料夾覆蓋的指令；
- **AI 的「快速修復（Quick Fix）」**：這是最危險的地雷！很多時候程式跑不起來，AI 會用極端偷懶、繞過驗證或關閉安全檢查的方式讓它「表面上能動」，暗地裡卻引入巨大漏洞；
- **關鍵系統與特權操作**：所有涉及資料庫遷移（Migration）、Production 部署與權限變更；
- **敏感資訊隔離**：嚴格設定 `.gitignore` 與模型忽略規則，杜絕 `.env` 或憑證檔案被餵入模型上下文。

## 🌿 解法三：Git Worktree 實戰！多分支物理隔離與原子化提交工作流

**【Miss Tika】**：最後一個問題是多人協作與並行開發。

大家可以試想：如果你在開發多個功能時，分支名稱全叫 `test1`、`test2`，Commit Message 寫得含糊不清，團隊協作會有多痛苦？

一個優秀的 Commit 必須具備兩個特質：**目的單一、敘述清晰**。

而在現代 AI 輔助開發時代，開發者常常需要同時跑多個功能、驗證不同解法，頻繁 `git checkout` 切換分支不僅繁瑣，還容易造成本地未提交檔案的衝突。

為了解決這個痛點，我強烈推薦大家使用 **Git Worktree**！

Git Worktree 是 Git 原生支援的強大功能：
- **傳統 Git**：一個 Repository 只有一個 Working Directory，切換 Branch 時所有檔案會在同一個目錄下被覆蓋變更；
- **Git Worktree**：共享同一個底層 `.git` 儲存庫，但允許你在本地同時開闢多個相互獨立的工作目錄（Working Trees），每個目錄各自綁定獨立的分支！

在 VS Code 中，你可以搭配 Git Worktree Manager 插件。當 AI 架構師幫你拆分出 `feature/auth` 與 `feature/game-logic` 兩個獨立規格時，你可以一鍵為它們建立兩個隔離目錄。

這帶來了巨大優勢：
1. **物理目錄隔離**：兩個功能的檔案完全獨立，彼此不污染，避免未提交程式碼互相踩踏；
2. **規格獨立綁定**：每個分支的工作目錄只專注於自己對應的 Spec 文件，AI 讀取的 Context 乾淨單純，絕不串味；
3. **原子化提交（Atomic Commit）**：每個分支的功能純粹，產出的 Commit Message 粒度適中、目標明確；
4. **衝突最小化與清晰合併**：在最後合併至 Main 分支時，依據相依性依序發起 PR，大幅降低 Merge Conflict。

## 🏁 結語與社群交流

**【Miss Tika】**：總結今天演講的三大核心 Takeaways：
1. **需求對齊先於代碼生成**：善用反向提問法，讓 AI 幫你挑出規格盲點，理清架構再動手；
2. **守住人工審查底線**：畫面光鮮不代表底層安全，針對破壞性操作與 Quick Fix 保持高度警惕；
3. **善用 Git Worktree 隔離並行開發**：落實單一功能分支與原子化提交，告別百變怪 PR！

用 AI 寫程式確實很爽、速度極快；但唯有建立嚴格的工程規範與安全意識，我們才能真正享受 AI 帶來的生產力，而不是被它產出的技術債掩埋！
