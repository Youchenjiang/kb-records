## 💡 照護媒合系統提案：家屬需求引導、照服員排程與服務打卡驗證

**【報告學員】**：老師好、各位同學好。我們這組發想的期末專案題目是「照護媒合系統」。因為我們觀察到家屬在找照顧服務員（照服員）的時候，經常卡在自己的照護需求說不是很清楚，加上坊間很多個案沒有用到系統化的媒合工具，導致後續照護出現糾紛或問題時沒有人進行處理與追蹤。所以我們就想設計一套線上媒合平台來解決這件事。

**【報告學員】**：我們這個系統總共規劃了三個核心角色：第一是「家屬」，第二是「照服員」，第三是「機構督導」。家屬端主要就是填寫被照顧者的各項評估指標與具體需求，然後在系統推薦後選擇合適的照服員開始排定照護時段。照護結束之後，照服員可以回報執行進度或安排休息；而照服員在接案管理上，家屬選擇他之後他可以選擇接手，如果確認接手，就會開始跟家屬在指定日期配合照護服務並記錄工作事項。

**【報告學員】**：第三個角色是機構督導，督導負責管理轄下所有照服員、後台帳號權限以及整體服務品質維護。回到家屬端的需求填寫，我們是設計用結構化的評估問卷來引導家屬。整個系統從評估到反饋大致分為八個步驟：家屬先註冊並建立被照顧者的基本個案資料，填寫評估問卷詳細說明需求；系統收到需求後，會依據條件推薦大概兩位合適的照服員供家屬挑選。

**【報告學員】**：家屬選定照服員後，照服員端會收到即時邀請，照服員可以選擇接受或婉拒。如果照服員婉拒，家屬就可以重新選擇推薦名單；如果照服員接受，雙方就可以透過系統的共享行事曆來安排具體的照護時間表。照護服務結束之後，家屬可以進行評價與回饋，這些反饋會直接同步給機構督導查看，並回饋到系統推薦機制的評分選項中，督導也能在後端即時掌握異常。

**【授課教師】**：好，麻煩簡報轉到前面一下。好，對對對。所以家屬這邊先註冊，然後填寫需求評估表單，系統進行推薦。那你們系統背後的推薦邏輯，目前有預設什麼算法嗎？

**【報告學員】**：報告老師，目前還沒有確定很複雜的演算法，現在主要就是依照家屬填寫的需求條件做規則篩選，因為我們還沒有累積大量的對比歷史資料，所以初期是規劃用簡單的規則或 AI 提取特徵來做推薦。

**【授課教師】**：OK，所以實際上你們第一階段沒有要刻意設計很複雜的機器學習推薦演算法，而是先確保功能跑得通，符合家屬在表單上填的需求。那好，家屬選了一位照服員之後，照服員再決定接不接案。那對照服員來說，你們系統會不會設計讓他能預先設定他所有的空閒時段？例如哪幾天、哪幾個時段是有空接案，哪些時段不行，這些時段管理功能都有規劃進去嗎？

**【報告學員】**：報告老師，會的，照服員會有個人的可用時段日曆可以勾選設定。

**【授課教師】**：好，因為我先設想實際的使用情境。如果這套系統要讓照服員跟家屬真的願意持續使用，一些輔助與信任機制是非常關鍵的。例如照服員實際去個案家中提供服務時，必須要有履約佐證資料。你們可以設計照服員抵達時透過手機 App 或行動網頁進行打卡報到，家屬端的手機也能即時跳出通知確認「照服員已抵達」，離開時再次打卡結案。

**【授課教師】**：這樣後台督導與家屬就能清清楚楚記錄什麼時候抵達、照顧了多久、什麼時候離開，既保障被照顧者的權益，也保護照服員不會產生工時爭議。那你們目前規劃是開發獨立的手機 App 還是響應式 Web 網站？

**【報告學員】**：我們目前規劃是以響應式 Web 網站為主，手機瀏覽器打開就可以直接使用，降低安裝門檻。

**【授課教師】**：好，Web 很好，手機瀏覽器能直接開很方便。這個方向市場需求確實很大，長照與居家照護的痛點非常明顯。那現場其他同學有沒有什麼提問或建議？好，沒有的話我們就謝謝第一組。

## 📑 研發處技管組產學合約審查小幫手：全校千件合約痛點與條款差異比對

**【授課教師】**：好，接下來是第二組。

**【報告學員】**：老師好、各位同學好。我們這組是跟學校研發處技術合作暨產學管理組（技管組）合作，針對他們的業務痛點開發一套「合約審查小幫手」。學校的教授們非常頻繁地跟校外單位、政府機關或民間企業進行產學合作，簽訂各種類型的產學合作合約書。

**【報告學員】**：但在實際簽約過程中，不同合作單位的合約書版本五花八門。有些廠商會拿中央大學的標準範本合約做修改，在裡面新增、刪除或修改某些條款；有些單位則堅持使用廠商自己的合約版本送過來學校。每次收到這些合約，技管組承辦同仁與學校法務都必須完全以人工方式逐字逐句進行稽核審查。

**【報告學員】**：承辦同仁人工審查時常常面臨四大痛點：第一是名詞一致性檢查，例如同一份合約前面叫「甲方」、後面寫成廠商簡稱，或者計畫名稱、主持人姓名、履約期程、經費金額在不同條文與附件中出現筆誤或不一致。第二是條款新增與修改比對，如果是以學校版本為基礎，廠商究竟改了哪些字句？承辦人必須拿出學校範本左右對照，非常吃力。

**【報告學員】**：第三是外部合約的條款缺漏與合規審核，如果廠商是用他們自己的範本，承辦人必須確認學校規定的必備保障條款（例如智財權歸屬、利益衝突迴避、保密協定、管轄法院等）有沒有被漏掉或新增了不利於學校的苛刻條款。第四是確認歷史與審查意見產出，目前承辦同仁要手動整理修改對照表與簽核意見，耗費大量行政時間。因此我們希望開發一套 AI 線上合約審查系統，自動完成條款結構化拆解與一致性比對。

**【報告學員】**：系統整體架構是：承辦人員上傳 Word 或 PDF 合約檔案到系統，後端先利用 Python 腳本將整份合約依據章節與條款進行階層化切割，拆成獨立的條目。我們不會把整篇幾十頁的合約一次性丟給語言模型，避免 context window 過長產生遺忘或幻覺；而是逐條送入模型與標準詞庫進行比對，標註出條款差異與缺失項目，最終產出一份結構化的條款比對清單與審查建議，供承辦人員進行最後的專業複核。

**【授課教師】**：好，報告得很清楚，我來補充一下研發處這個題目的背景。大家可能不知道，全校現在有大概 700 位專任教師，每年執行的國科會計畫、產學合作計畫、政府標案加起來有上千件！而全校研發處專門審查合約的法務人員，只有 2 位！兩位法務同仁每年要審查上千件合約，工作壓力極其巨大。

**【授課教師】**：更麻煩的是，合約審查不是只看一次就好。學校法務提出修改意見退回給廠商，廠商法務看過後又會修改，雙方來來回回攻防協商三到五次是家常便飯。在頻繁的往返修改過程中，廠商有沒有偷偷改了某一條裡面的幾個關鍵字？承辦同仁根本防不勝防，每一次往返都要重新人眼抓漏，眼睛負擔非常沉重。

## 🛡️ 地端大語言模型 TAIDE 8B/12B 部署：保護學校合約機密與跨版本 Diff

**【授課教師】**：所以當時研發處找我討論時，我們就認為大語言模型（LLM）對長文本的語意理解與邏輯比對能力非常適合這個場景。重點是把兩份合約之間的差異精準 Diff 出來，並設計友善的雙欄對照介面，讓承辦人一眼就能看出哪裡被動過手腳。但有一點非常重要：**最後的審查責任仍然必須由承辦人與法務同仁負責，AI 只是輔助工具，絕對不能完全自動化替代人類簽核！**

**【報告學員】**：是的老師，我們的定位就是輔助小幫手，自動標註並高亮潛在風險條款，最後決策權仍在承辦人。

**【授課教師】**：很好。另外有一個非常關鍵的資安與法規合規問題大家務必留意：產學合約裡面涉及大量商業機密、專利技術細節與合作經費，**這些未公開的機密文件絕對不能隨便上傳到外部公有雲 API（例如 OpenAI ChatGPT 或海外伺服器）！**

**【報告學員】**：報告老師，我們昨天跟技管組討論時也有共識，考量到機密性與法規要求，目前規劃是部署在地端伺服器（on-premise）的開源大語言模型來做推論。

**【授課教師】**：很好，走地端推論是正確方向。而且國家現在公務與學術機關對於資安有嚴格規範，不能使用中國大陸開源的基礎模型。在開源繁體中文模型方面，我強烈建議你們採用國科會主導開發的 **TAIDE** 模型！目前 TAIDE 有 8B、12B 甚至 30B 等不同參數量版本，針對臺灣法律用語與繁體中文語境做了非常好的指令微調。

**【授課教師】**：目前研發處現有的地端 GPU 機器，跑 8B 到 12B 的模型非常順暢。如果開發過程中需要測試不同的大語言模型或需要額外的運算資源與 API Token，到時候跟我說，我可以用研發處的數位轉型經費來支援你們，幫你們把環境生出來！

**【授課教師】**：最後提醒一點：除了拿學校範本跟廠商版本做比對之外，你們系統也要支援「同一份合約前後版本」的比對。也就是廠商第二次送過來的 Version 2 跟先前的 Version 1 之間到底改了什麼，這在實務攻防上非常有價值。好，第二組做得很棒，我們謝謝第二組！

## 🏢 社區住宅智慧服務系統：Docker 跨平台封閉式部署與隱私 PIN 碼機制

**【報告學員】**：各位同學、老師好，我們是第三組。我們今天要發表的期末專題提案是「社區住宅智慧服務系統」。現代集合式住宅基本上都有管委會，日常營運牽涉到管委會公告、住戶投票、修繕反映與包裹收發等庶務。

**【報告學員】**：大家知道目前市場上佔有率最高的是「智生活」App，很多同學家裡或租屋處都在用。但我們訪談了周遭住戶與管理員，大家普遍覺得智生活功能過於臃腫雜亂、商業廣告多、收費高昂，而且住戶個資與社區公告全部存放在雲端第三方平台，缺乏獨立自主性。台中有許多七期豪宅建商會自己開發獨立封閉的管理系統，所以我們希望開發一套輕量、簡潔、高隱私且完全封閉式的開源社區服務平台。

**【報告學員】**：在系統架構上，我們採用 **Docker** 容器化技術封裝整套服務，不論管委會使用的是 Windows、macOS 還是 Linux 舊電腦，只要安裝 Docker 就能一鍵快速部署。住戶端完全不需要下載或安裝任何手機 App，只要使用瀏覽器輸入區域網路 IP 就能直接操作，對長輩非常友善。

**【報告學員】**：在隱私保護設計上，我們採取零住戶個資暴露機制。系統資料庫中完全不記錄住戶的真實姓名、身分證字號或職業，只記錄「棟別戶號」與一組由雜湊（Hash）演算法產生的 6 位數匿名 PIN 碼。住戶投票時，該 PIN 碼使用過一次即自動作廢，避免重複投票；包裹領取時，住戶只要憑戶號與一次性安全碼即可領件，即使管委會管理員也無法隨意刺探住戶隱私。住戶反映公共修繕問題時，還可以自行選擇公開陳情或私密給管委會，兼顧透明度與隱私。

## 🔌 社區硬體通訊架構：對講機線路復用、單機備份與商用落地考量

**【授課教師】**：好，這組的規劃非常完整，簡報也很有商業產品發表會的架勢。我有幾個實務問題想請教：你們剛提到住戶透過手機瀏覽器連進去社區系統，那在實體網路與硬體佈線上，你們是打算怎麼實現？因為傳統公寓或社區住戶回家後都是連自己家的中華電信 Wi-Fi，你們的區域網路要如何涵蓋到這十戶、二十戶住戶？

**【報告學員】**：報告老師，我們一開始設定的目標客群是雙併、門對門，大概 10 戶到 20 戶以內的傳統華廈或小型公寓。在這種小規模場域，管理室或公共樓梯間架設一個長距離 Wi-Fi 訊號源就能涵蓋。

**【授課教師】**：如果是小型公寓確實比較好解決。但如果稍微大一點的社區，每戶家裡的實體網路線都是各自拉中華電信光世代或第四台 Cable，彼此在不同網段。不過我想到一個解法給你們參考：現在大多數集合住宅每戶家裡都有安裝跟管理室通話的「室內對講機系統」，對講機走的是社區內部的獨立弱電線路。你們其實可以研究透過對講機線路復用或是建築內部廣播弱電箱走區域網路，這樣就能把封閉式網路直接通到每一戶門口。

**【授課教師】**：另外第二點，既然你們強調全單機、封閉式本機資料庫運作，那一定要特別注意「資料備份與容災機制」。萬一管理室那台電腦硬碟壞掉或主機故障，所有的公告、包裹紀錄與投票歷程如果不見了，管委會會面臨嚴重爭議。你們可以設計定期加密匯出備份檔案至外接儲存裝置或離線雙備份（3-2-1 備份原則）。

**【授課教師】**：整體而言，這三個專案題目都非常有針對性，一個聚焦高齡長照媒合、一個深入研發處法務合約痛點、一個挑戰智慧社區微型化部署。大家都走出象牙塔、對接到真實的使用者情境，規劃非常扎實。好，我們今天早上就先討論到這邊，大家辛苦了，我們休息一下！
