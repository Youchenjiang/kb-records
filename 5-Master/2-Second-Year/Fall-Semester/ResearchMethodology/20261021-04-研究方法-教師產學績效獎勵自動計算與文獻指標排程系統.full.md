## 🏆 教師產學績效獎勵自動計算：448 位專任教師與 1700 萬獎金試算規則

**【報告學員】**：老師好、各位同學好。我們這組的題目是針對研發處最重要的「教師產學績效獎勵自動計算與文獻指標排程系統」。目前學校每年計算教師研究成果獎勵的流程非常繁重，在前置步驟中，系統必須從電算中心、研發系統以及外部學術資料庫匯入資料，經過清洗去除重複後，依據法規公式進行個人指標計算與責任判定。

**【報告學員】**：以目前全校的規模來說，全校總共有 448 位專任教師，在初步試算中，有 99 位老師通過基本獎勵條件，共有 257 位老師至少符合其中一項評估指標。全校預估發放的獎勵總金額高達 1,700 多萬元！其中金額佔比最大宗的是「論文高被引用獎」，總計有 116 位老師符合資格，瓜分了 1,300 多萬元，佔整體發放金額的 76%。

**【報告學員】**：這項業務最困難的地方在於：每位老師符合的獎項類別不同、每項指標的權重標準不同、第一作者或通訊作者身分認定不同，加上跨年度重複計列排除等複雜邏輯。如果完全依賴人工整理與人眼核算，只要任何一個環節步驟計算錯誤，最後產生的獎金差異動輒數萬甚至十幾萬元。因此我們系統的核心價值就是把法規計算規則完全程式化、存檔固定下來，每次都跑同一套嚴謹邏輯，並產出清單供行政同仁逐一覆核。

**【報告學員】**：在角色與功能規劃上，系統包含兩個主要介面：第一是「研發處後台」，具備月度版本確認機制與異議修訂審查流程；第二是「教師端平台」，老師能登入查看當月份的個人積分排名、名次升降趨勢以及被引用的文獻清單。若老師對計算結果有疑義，可直接在線上提出異議建議並上傳佐證文件，後台同仁進行抽查與人工審核。

## 💻 敏捷開發實務與架構維護性：非結構化資料整合與電算中心介接

**【報告學員】**：在技術與專案管理實踐上，我們一開始討論時業務單位曾問我們：是要用 Excel 匯入匯出，還是直接跟電算中心串接 API？考量到如果一開始就向電算中心申請開 API，行政往返確認會耽誤非常多時間。因此我們的策略是先根據現有資料設計好欄位與資料庫架構，日後再協調電算中心開出符合規格的資料導出服務。

**【報告學員】**：此外，因為各學院的評鑑加分項目會隨政策不斷調整，欄位尚未完全結構化，因此我們後端搭配了非結構化資料庫來支援彈性擴充。在團隊分工上，我們貫徹敏捷開發（Agile），兩位善於溝通的組員投入 80% 的時間在業務訪談與系統分析上，確保介面貼合行政同仁習慣；工程組員則投入 20% 的時間專注於核心計算邏輯與測試案例開發。

**【授課教師】**：好，前一組這個專案非常重要！大家要以非常嚴肅、嚴謹的態度來看待這套系統。為什麼呢？就如同剛才簡報所說的：這套系統每年影響到全校老師的獎勵金高達 1,700 多萬元！

**【授課教師】**：大家要知道，大學裡面的教授對於學術成果與獎金這件事情是「錙銖必較」的！以往學校每年算出來之後，都會有一堆老師跑到研發處來拍桌子抗議，吵著說：「你們的計算演算法不對！我的演算法才對！為什麼我少了一篇 Q1？」而資管系的同學如果跟老師溝通，壓力會極大，因為在大學校園體制裡，教授往往比行政同仁強勢，最後都要請我們這種兼任主管出面跟老師溝通協調，常常也是低聲下氣賠不是。

**【授課教師】**：而且這套系統牽涉到一個體制責任的根本性轉移：以前學校只有所謂的「彈性薪資（彈薪）」，彈薪機制是「被動申請制」，也就是由老師自己填報、自己算分，研發處只負責查核老師有沒有填錯，算錯退件責任在老師身上。但現在這套績效獎勵是「主動給獎制」，由研發處主動抓資料試算發錢。主動給獎一旦算錯，責任完全落在研發處！如果不該得獎的老師誤發了三萬元，事後追回老師絕對大發雷霆；該得獎的老師漏發了，老師會追究到底。

**【授課教師】**：另外要提醒大家留意規則複雜度：第一，已經領取教育部或學校高額彈性薪資（例如講座教授每月加給 6 到 15 萬元且終身延退到 70 歲）的老師，依規定是直接排除不能重複領取這項個人貢獻獎的；第二，全校各學院每年都會發布「掠奪性期刊排除清單」，理工學院、生醫理工學院與管理學院認定的黑名單都不盡相同，甚至這本期刊在管院算數、在工院不算數。系統必須設計動態規則設定介面，允許隨每學年法規彈性微調，才能真正上線長期使用。

## 🎵 多人出遊共乘音樂清單推薦平台：Spotify API 串接與喜好權重隨機交錯

**【報告學員】**：老師好，我們這組的題目是「多人共乘音樂清單推薦平台」。我們觀察到很多人跟朋友或家人開車出遊時，往往由駕駛一人決定播放歌單。但每個人喜歡的曲風不同，遇到不喜歡的歌又礙於情面不好意思切歌，導致車內氣氛尷尬。

**【報告學員】**：因此我們設計了一個共乘音樂共享平台：由主辦人建立虛擬房間，車上乘客加入房間後，可以匯入各自的 Spotify 歌單或曲風喜好。系統後端透過 Spotify Web API 讀取曲目特徵，利用動態加權演算法將每位乘客喜歡的歌曲進行交錯隨機排序，確保每個人的愛歌都能被輪流播放，不會由單一曲風壟斷。

**【報告學員】**：在行車過程中，乘客可以即時按下「喜歡」或「不喜歡」來動態微調後續待播清單的權重；行程結束後，系統還會生成該次旅程的音樂回顧清單供大家收藏。

**【授課教師】**：這個題目很有生活情境趣味，切入點很生活化。不過要注意的是，Spotify 的 API 授權與播放控制在非 Premium 用戶或第三方整合上有較多權限限制，實作時要先確認 API 呼叫額度與端點限制。

## 🐾 寵物認養媒合、產學合約轉填表一表二與連鎖健身房系統評析

**【報告學員】**：接下來我們這組介紹的是「寵物認養媒合平台」。現行公立收容所的認養資訊分散，申請審查流程冗長。我們系統將流程整合為三個階段：認養前提供生活型態與寵物習性智能問卷配對；認養中提供線上申請、收容所審查通知與進度追蹤；認養後則延伸提供社群交流、照護問答與附近寵物醫療用品指引，藉由全生命週期服務提高認養成功率與飼養責任感。

**【報告學員】**：另一組同學發表的題目是「產學合約書轉填表一表二小幫手」。前面第二組是做簽約前的合約比對審查，而我們這組則是針對「簽約完成後」的行政痛點：教授接到產學案簽完約後，必須在研發系統填寫繁瑣的表一、表二（填寫計畫基本資料、人事費、管理費分配等）。許多老師根本不想花時間理解研發系統欄位邏輯，往往打電話轟炸行政承辦人。我們的小幫手是透過文字解析讀取已簽署的 PDF 合約，自動擷取案名、經費、起訖日期、合作機構等，直接生成填寫範本甚至一鍵帶入，大幅降低老師負擔。

**【報告學員】**：最後一組同學發表的是「連鎖健身房多門市營運與課程管理系統」。針對大型健身俱樂部現行會籍、教練課程預約與金流核銷系統互相割裂的痛點，以三層權限架構（總部品牌、各分店門市、會員端）整合會員 App、教練排課行事曆與合約扣款核銷流程。

**【授課教師】**：好，今天各組的發表都非常豐富！特別是研發處的產學合約轉填表一表二，跟前面簽約前審查剛好形成前後呼應的完整拼圖；產學獎勵金計算更是牽涉千萬公帑的核心硬仗。大家期末專案切勿只停留在玩具系統，要持續深入業務痛點、做好邊界驗證與彈性設計。謝謝大家，我們今天就到這裡下課！
