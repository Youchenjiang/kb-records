## 課堂背景與技術範疇

本堂課為 10/20「網路架構」課程的第一節課。前半段為學生專題報告，主題為「Proxmox VE（PVE）開源虛擬化伺服器管理平台與校園失物招領系統架構實作」；後半段則由授課教師針對乙太網路交換機（Switch）轉發表（Forwarding Table）尋徑邏輯與樹狀無環拓撲展開深度講授。

專題報告核心內容涵蓋：
1. **PVE vs. VMware vSphere 企業選型評估**：
   - 博通（Broadcom）收購 VMware 後改採全面訂閱制，推升中小企業授權成本，驅使業界轉向基於 Debian Linux 之開源 PVE（AGPLv3）。
   - 核心虛擬化技術差異：KVM 完整虛擬機器（硬體隔離、可跑 Windows/Linux、資源開銷較大）vs. LXC Linux 容器（共享主機核心、輕量快速、節省資源）。
2. **校園失物招領系統（Campus Lost & Found System）微服務架構**：
   - 採用四大獨立 LXC 容器：CT 105（Cloudflare Tunnel 對外安全通道）、CT 102（Nginx + React 前端介面與反向代理）、CT 101（Gunicorn + Flask 後端 API 與圖片處理）、CT 103（PostgreSQL 14 資料庫，5432 埠）。
   - 拓撲隔離與管理邊界：內部私有網段 `10.10.10.0/24`；外網流量透過 Cloudflare Tunnel 由內向外建立安全通道，免開路由器公開埠；管理流量則透過 Tailscale（WireGuard Mesh VPN）與 ACL 標籤精準授權存取 Web GUI（8006 埠）。
   - 監控與高可用演練：導入 Uptime Kuma 進行 20 秒週期健康探測，異常時發送 Discord Webhook 即時告警；使用 Hey 進行壓力測試；解析 PVE 快照（Snapshot）與三種備份模式（Snapshot / Suspend / Stop）及 Corosync Quorum 多數決防腦裂機制。

授課教師於後半段回歸網路交換機本質，以課本架構圖為基礎，詳解交換機轉發表（Switch Table）如何透過輸入埠（Ingress Port）學習來源 MAC，並在轉發時精準比對目的 MAC 映射至唯一輸出埠（Egress Port），闡明樹狀無環拓撲在數學上保障「任意兩點間唯一路徑」之核心防禦價值。

## 課堂完整對話記錄

**【學生報告者】**：老師好、各位同學好。我們這組今天為大家帶來的是 Proxmox VE（PVE）虛擬化伺服器管理平台的專案報告，現場也會有實際系統的展示與功能介紹。

**【學生報告者】**：這是我們的報告目錄：第一部分我們會簡單介紹什麼是 PVE，以及 PVE 和商業市場龍頭 VMware 之間的重要差異；第二部分我們會介紹我們在實驗室主機上實際架設的「校園失物招領系統」，包含整體網路架構與容器拆分；第三部分我們會現場示範 PVE 的管理功能，包括 Web UI、Tailscale VPN 存取、快照、備份與叢集機制；第四部分會交代我們這份報告的製作流程與 AI 使用情況；最後是我們的心得感想與參考資料。

**【學生報告者】**：首先是 PVE 的簡介。什麼是 PVE（Proxmox Virtual Environment）呢？它是一套建立在 Debian Linux 基礎上的企業級開源虛擬化伺服器管理平台。它的底層直接運作在實體主機的 CPU、記憶體與硬碟等實體硬體上；在硬體之上運行的是 Debian 作業系統；而在 Debian 之上，PVE 整合了兩種核心虛擬化技術：

**【學生報告者】**：第一種是 KVM（Kernel-based Virtual Machine）虛擬機器，它將實體主機的物理硬體資源虛擬化分配給虛擬機器使用，每台 VM 都有自己獨立的作業系統核心；第二種是 LXC（Linux Containers）容器，它是基於 Linux 核心的 cgroups 與 namespaces 隔離機制，讓每個容器能夠高效共享主機核心。最上層則是 PVE 內建的網頁管理介面，安裝完成後，直接在瀏覽器輸入 `https://IP:8006` 就能進入圖形化管理面板。

**【學生報告者】**：在授權方面，PVE 是採用 GNU AGPLv3 自由軟體授權，軟體本身完全開源免費。企業如果需要官方商業支援，可以付費購買企業訂閱倉儲（Enterprise Repository）與技術支援服務。

**【學生報告者】**：上一頁我們提到 PVE 同時提供 KVM 虛擬機器與 LXC 容器兩種技術，我們來比較一下這兩者的優劣：KVM 屬於全虛擬化，它完整模擬整台電腦，擁有獨立的 OS 核心，可以自由安裝 Windows、Linux 或 FreeBSD，隔離性最高，但缺點是比較消耗硬體資源，開機啟動速度較慢。

**【學生報告者】**：而 LXC 容器則是共享主機的 Linux 核心，只能運行 Linux 作業系統，隔離等級雖然比虛擬機器略低，但優勢是極度輕量化、啟動速度達到秒級，而且非常節省記憶體與 CPU 資源。因為我們這次專案的失物招領系統，前端、後端與資料庫全部都是 Linux 服務，考量到實體主機資源有限，我們全數選擇使用 LXC 容器來構建。

**【學生報告者】**：目前有許多中小型企業開始偏向採用 PVE 而非 VMware，關鍵原因在於授權成本。自從 VMware 被博通（Broadcom）收購之後，原廠將過去的永久授權買斷制徹底取消，全面強制改為高昂的年費訂閱制，讓許多企業的 IT 預算大幅暴增。

**【學生報告者】**：在功能對比上：PVE 內建免費的 Web UI，單機安裝即可直接管理；而 VMware 若要跨主機集中管理，必須額外購買昂貴的 vCenter Server；容器支援方面，PVE 預設原生整合 LXC，VMware 則需額外付費引進 Tanzu 架構；在高可用性叢集（HA Cluster）與備份方面，PVE 完全內建且不限制節點數，還提供開源的 Proxmox Backup Server（PBS），而 VMware 則往往需要依賴 Veeam 等第三方商業備份軟體。

**【學生報告者】**：介紹完 PVE 之後，接下來向大家介紹我們的實作專案——「校園失物招領系統」。這是我們系統的公開網址，大家有興趣的話可以拿出手機掃描投影幕上的 QR Code 連線體驗，倒數五秒：五、四、三、二、一，好，我們切換到下一頁。

**【學生報告者】**：我們這個校園失物招領系統主要分為兩種使用者角色：第一個是「拾獲者」，拾獲者必須使用學校學號進行註冊與登入。我們後端特別針對中央大學的學號編碼規則設計了正規表達式校驗，非正規學號是無法通過註冊的。登入成功後，拾獲者可以上傳撿到的物品照片、填寫拾獲地點、分類與時間並發布貼文；當物品歸還失主後，拾獲者可以一鍵標記為「已歸還」。

**【學生報告者】**：第二個角色是「失主」，失主在不用登入的情況下，就可以直接在首頁瀏覽最新遺失物清單，並依照類別（如皮夾、耳機、證件、傘具等八大分類）進行關鍵字篩選；點進貼文詳情，失主就能看到拾獲者的聯繫方式。在技術棧方面，前端我們採用 React 配合 Ant Design，後端使用 Python Flask 撰寫 RESTful API，資料庫則使用 PostgreSQL。

**【學生報告者】**：在系統服務架構上，我們將整套系統拆分為四個獨立的 LXC 容器：
- 第一個是 CT 105 容器，負責建立 Cloudflare Tunnel 對外安全通道；
- 第二個是 CT 102 容器，部署 Nginx 與 React，負責前端網頁靜態資源渲染與 API 請求反向代理；
- 第三個是 CT 101 容器，運行 Gunicorn 與 Flask，負責處理商業邏輯與照片上傳處理；
- 第四個是 CT 103 容器，運行 PostgreSQL 資料庫，專門儲存使用者帳號與物品貼文資料。

**【學生報告者】**：我們將每項服務拆成獨立容器，方便個別進行資源調配、版本更新與定時備份。大家可以看到容器編號與內網 IP 末碼保持一致（例如 10.10.10.101 對應 CT 101），維護時一目了然。

**【學生報告者】**：在網路拓撲設計上，我們做了嚴格的內外網與管理平面隔離：訪客的手機瀏覽器透過 HTTPS 訪問網域名稱，流量首先抵達 Cloudflare 邊緣網路，接著透過 Cloudflare Tunnel（雲端加密通道）穿透進入內網的 CT 105 容器。

**【學生報告者】**：我們的私有內網網段是 `10.10.10.0/24`，因為使用了 Cloudflare Tunnel 由內向外的主動長連線技術，學校校園網路的閘道路由器完全不需要為我們開啟任何對外對應埠（Port Forwarding），外網駭客根本無法直接對我們內網進行埠掃描，防火牆防禦強度極高。

**【學生報告者】**：流量進入 CT 105 後，轉發至 CT 102 前端 Nginx；Nginx 再將 `/api` 請求丟給 CT 101 後端 Flask；後端最後透過 5432 埠向 CT 103 PostgreSQL 查詢資料。而管理員要進入 PVE 底層管理介面（8006 埠），則必須透過 Tailscale（基於 WireGuard 的 Mesh VPN）建立虛擬專用網路，經過身分驗證與 ACL 標籤過濾後才能存取，這使得服務流量與管理流量達到 100% 物理與邏輯上的分離。

**【學生報告者】**：為了驗證我們的架構能否承受校園尖峰流量，我們使用開源壓測工具 Hey 進行了壓力測試。在有 Cloudflare 與安全通道過濾的外網壓測情境下，每小時成功處理一萬筆請求，主機 CPU 使用率穩定在 4%~6% 之間；而在內網直連壓測中，總發送請求數達到四十萬筆，CPU 短暫飆升至 18%，但系統完全沒有發生任何崩潰（Crash），充分證明此容器架構足以支撐校園級別的使用需求。

**【學生報告者】**：此外，在系統維運監控方面，我們部署了開源監控平台 **Uptime Kuma**。我們為前端、後端、資料庫與 Tunnel 四個容器分別建立了監控專案，每隔 20 秒發送一次 HTTP 或 TCP Ping。如果服務發生異常，Uptime Kuma 會在第一時間透過 Webhook 發送警報至開發團隊的 Discord 頻道，讓工程師無需整天盯著儀表板也能秒級獲知服務異常。

**【學生報告者】**：在 PVE 核心管理功能展示中，我們示範了 PVE 強大的快照（Snapshot）與備份（Backup）機制：快照主要記錄記憶體與磁碟當前狀態，支援秒級 Rollback 回滾，但快照檔案與原容器共存於同一個磁碟池中，若實體硬碟毀損，快照也會隨之遺失。因此企業環境必須配合 PVE 備份功能（VZDump），將容器設定與資料完整打包匯出至外部儲存裝置。

**【學生報告者】**：PVE 備份支援三種模式：第一種是 Snapshot 模式，容器不中斷服務，背景邊拍快照邊非同步備份，服務零停機；第二種是 Suspend 模式，短暫凍結容器寫入完成備份後迅速恢復；第三種是 Stop 模式，直接將容器完全關機進行冷備份，資料一致性最高，但需要較長停機維護時間。

**【學生報告者】**：最後在叢集（Cluster）與高可用（HA）架構上，PVE 整合了 Corosync 叢集通訊協定與 Quorum（多數決投票機制）。當網路發生分割（Split-Brain）時，只有擁有超過半數（>50%）投票權的節點分區才被允許繼續執行並接管服務，避免多個孤島節點同時寫入共享儲存造成資料毀損。因為我們專案只有一台實體主機，所以本次僅就單節點架構進行實作。以上是我們的報告，謝謝大家！

**【授課教師】**：好，非常謝謝這組同學。大家給他們熱烈的掌聲！他們這組介紹得非常深入且完整，雖然時間稍微超過了一點點，但內容非常扎實。我想請大家回頭看他們的第十三頁簡報。

**【授課教師】**：這組同學的實作有兩個非常值得全班借鏡與學習的架構亮點：第一個亮點，是他們在網路邊界與管理通道上的嚴格隔離。在企業級私有雲中，管理介面（Web UI）絕對不能赤裸裸地暴露在公網給全世界連線！他們透過 Cloudflare Tunnel 處理對外服務，並利用 Tailscale Mesh VPN 搭配嚴格的 ACL 標籤來保護 PVE 8006 管理埠，不在授權白名單內的設備連連線機會都沒有，這是非常高水準的資安縱深防禦思維。

**【授課教師】**：第二個亮點，是他們對多容器生命週期與資料相依性的掌握。在實務上，像這樣規模的虛擬化機房管理，如果是在大型企業租用公有雲或購買 VMware 授權，一年的軟體維護費與授權費動輒數百萬台幣。大家如果能在研究所階段把 PVE、Debian 系統調校、網路拓撲與監控告警這套工程實戰能力徹底掌握，將來進到企業 IT 或 DevOps 部門，年薪隨便都是百萬起跳，這就是真正的核心專業技能！

**【授課教師】**：好，我們把投影切換回老師的講義。現在只剩下十幾分鐘，我們回到課本上的網路交換架構。請大家翻開課本的網路拓撲圖，有沒有注意到剛才投影上畫的這幾台「網路交換機（Switch）」？

**【授課教師】**：在網路架構中，每一台交換機內部都維護著一張極為核心的表格——也就是 **交換機轉發表（Switch Forwarding Table）**，有時候我們也稱它為 MAC 地址表（MAC Address Table）。

**【授課教師】**：請大家仔細看這張轉發表，它的結構主要包含兩個關鍵欄位：第一個欄位是「實體連接埠（Port）」，也就是交換機機身上插著網路線的實體插孔（例如 Port 1、Port 2、Port 3……）；第二個欄位則是「目的硬體地址（Destination MAC Address）」，標記著該連接埠對外連接著哪一台主機或哪一個網段。

**【授課教師】**：當我們的實體網路線路接好之後，每一台交換機就開始透過封包流動進行「地址學習（Address Learning）」。當來源主機送出一個封包時，交換機會先記下這個封包是從「第幾個 Port」進來的、它的「來源 MAC」是什麼，這就在轉發表中建立了一筆學習記錄。

**【授課教師】**：那當交換機要轉發封包時呢？假設來源主機發起了一個連線請求，目的地是要送到右下角編號 1 的主機。這時候交換機收到封包，它立刻查詢內部的轉發表：目的地 MAC 為 1，對應的輸出埠是 Port 5。於是交換機毫不猶豫，精準地將封包從 Port 5 拋送出去，封包就順利傳輸到下一台交換機（Switch 2）。

**【授課教師】**：Switch 2 收到封包後，同樣查表比對目的地，再將封包從對應的連接埠送出，一路接力直到抵達最終的目標主機。

**【授課教師】**：大家注意觀察這張轉發表的一個數學特性：在轉發表中，左邊的 Port 欄位有沒有可能重複？有可能，因為同一個連接埠後面可能接了一個集線器或另一台交換機，連接著多台主機；但是右邊的「目的 MAC 地址」在整張表中會不會重複？絕對不會重複！

**【授課教師】**：這代表什麼數學意涵？這代表在一個標準運作的二層區域網路中，整體的拓撲結構必須像是一棵「樹（Tree）」一樣！從網路中的任何一個起點到任何一個終點，在任何給定時刻，永遠只有一條唯一的路徑可以通行！絕對不能存在迴圈或環路，否則廣播封包會在交換機之間無窮循環，瞬間引發可怕的「廣播風暴（Broadcast Storm）」而徹底癱瘓全網！

**【授課教師】**：好，轉發表的基本尋徑概念我們今天先講到這裡。請大家回去務必把課本這一段的圖文說明仔細讀完。我們休息十分鐘，下節課我們請下一組同學進行報告，大家休息！
