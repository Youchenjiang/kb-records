## 課堂背景與技術範疇

本堂課為 10/20「網路架構」課程的第二節課。前半段由江榮輝、黃宏奇、王紅麗、郭紅勳、張樂同學進行專題報告——「基於 Google Cloud Run 的外送排單系統自動伸縮（Auto Scaling）架構與壓測實證」；後半段則由授課教師針對簡報架構、工程邏輯與雲端極限場景進行深度講評，並銜接二層網路交換機轉發機制。

專題報告深入剖析現代雲端自動伸縮的四大演進階段：
1. **實體機房時代（Bare Metal）**：採購、組裝與上架需數天至數週，無法應對秒級突發流量。
2. **虛擬機器時代（AWS EC2 Auto Scaling, 2009）**：以完整虛擬機為擴充單位，開機需 3~5 分鐘，以小時計費。
3. **容器編排時代（Kubernetes HPA, 2014）**：以 Pod 為單位，擴展時間縮短至 1 分鐘內，依賴 CPU/Memory 資源利用率指標。
4. **Serverless 容器時代（Google Cloud Run / Knative）**：以 HTTP 請求並發量（Request Concurrency）為觸發訊號，百毫秒級極速擴縮，支援縮容至零（Scale-to-Zero），毫秒級精確計費。

團隊設計了一套具備雙重負載特性的「外送排單模擬系統」：單次計算較重的「訂單派單」與每 2 秒高頻執行 Dijkstra 最短路徑演算法的「配送追蹤」。為了消除共享資料庫成為效能瓶頸的干擾變因，系統採用「無狀態客戶端攜帶資料」設計。現場透過 QR Code 動員全班 60 多位同學即時下單，並同步啟動每秒 30 位新使用者的壓力測試腳本，實證「固定 1 台實體（對照組）」與「自動擴充至 20 台（實驗組）」的巨大差異：固定版成功率暴跌至 9% 且延遲飆升至 3.6 秒，而自動擴充版在 26 秒內迅速拉升至 18 台實例，成功率維持 100% 且延遲保持在毫秒級。

授課教師在講評中肯定其即時互動與觀測儀表板之工程水準，同時提出架構簡報的「受眾視角原則」，指明應將核心動機與展示前置，並進一步探討阿里巴巴「雙十一」等千萬級 QPS 極端場景下，公有雲通用 Auto Scaling 面臨之物理極限與架構分流策略。

## 課堂完整對話記錄

**【學生報告者（江榮輝）】**：老師好、各位同學好。我們這組今天的主題是「基於 Google Cloud Run 的外送排單系統自動伸縮（Auto Scaling）特性展示與壓測實證」。我是江榮輝，我們組員還有黃宏奇、王紅麗、郭紅勳以及張樂。

**【學生報告者（江榮輝）】**：首先由我為大家介紹：為什麼現代系統需要 Auto Scaling？Auto Scaling 的核心本質是什麼？以及從實體機房到 Serverless 容器的演進歷史。

**【學生報告者（江榮輝）】**：我們以大家最常碰到的生活經驗為例：大家一定都有喜歡的歌手或樂團，當他們舉辦大型萬人演唱會時，大家都會在售票系統開放的瞬間準時搶票。但在準點按下的那一刻，大家通常會碰到三種情況：第一種是幸運立即搶到票；第二種是看到網頁轉圈圈轉了十幾分鐘，最後彈出「已無票券」；第三種則是我們今天要探討的——直接跳出「HTTP 504 Gateway Timeout」伺服器超時崩潰！

**【學生報告者（江榮輝）】**：為什麼會這樣？因為傳統售票系統架設在固定規格的實體機房或固定主機上，無法瞬時自動擴充伺服器算力。當數十萬個連線瞬間湧入，伺服器算力直接被灌爆，導致整個系統卡死。

**【學生報告者（江榮輝）】**：面對這種突發性的高流量，傳統伺服器往往只能採取兩種固定配置策略，但兩者都有嚴重的致命缺點：第一種是「以平日離峰流量做配置」。在平日沒有大型活動時系統運作順暢，但一旦遇到萬人搶票，CPU 使用率瞬間飆到 100%，請求全面超時，系統直接癱瘓，這會重創企業的服務可用度（SLA）並導致顧客大量流失；第二種是「依歷史最高峰值流量做配置」，為了應付突發流量常態性租用大量機器。但萬人搶票一年可能只有幾天，在絕大多數閒置時間裡，企業依然必須持續支付高昂的硬體租金與電費維護成本，極度不符合成本效益。

**【學生報告者（江榮輝）】**：在這種兩難之下，解決方案就是——讓系統的運算資源能夠隨著即時負載「自動伸縮」，這就是 **Auto Scaling** 的核心本質！在雲端系統中，根據即時承受的負載（如 HTTP 請求量、CPU 利用率），自動動態增加運算資源以確保服務平穩；當尖峰流量消退後，自動縮減機器規模以節省閒置開支，完美兼顧高可用性（High Availability）與成本最佳化。

**【學生報告者（江榮輝）】**：回顧 Auto Scaling 的演進歷史，主要經歷了四個世代：
1. **實體機房時代**：完全無法自動擴充。企業要擴充必須先向原廠採購硬體伺服器、等待物流、工程師進機房組裝上架與佈線，往往耗費數天至數週，根本無法應對任何突發流量；
2. **虛擬機器時代（AWS EC2 Auto Scaling, 2009）**：雲端運算成熟後，AWS 首創可依負載自動增減虛擬機器（VM）。但擴充的基本單位是整台 VM，冷啟動開機往往需要 3 到 5 分鐘，面對秒級突發暴增的流量，往往機器還沒開好系統就已經先掛掉了，而且在 2017 年以前是以整小時計費；
3. **容器編排時代（Kubernetes HPA, 2014）**：Google 開源 Kubernetes 導入了 HPA（Horizontal Pod Autoscaler），以輕量化 Pod 為擴充單位，部署時間大幅壓低至一分鐘以內。但其局限在於當底層節點（Node）資源耗盡時，依然需要回頭擴展底層 VM；
4. **現代 Serverless 容器時代（Google Cloud Run）**：這是我們本次系統採用的核心架構。最小處理單位極致輕量化，以 HTTP 請求並發量（Concurrency）為觸發訊號。當偵測到突發流量湧入時，系統在「百毫秒級別」就能自動擴充或縮容；在極端離峰無人使用時，甚至能縮容至零（Scale-to-Zero），完全不產生任何計費支出。

**【學生報告者】**：接下來由我為大家解析：一個外部請求進入 Google 基礎架構後，Cloud Run 是如何完成路由與調度的？

**【學生報告者】**：外部流量主要會經歷四個關鍵階段：
- **階段一：DNS 與 Anycast 邊緣接入**。用戶請求透過 Anycast IP 自動導向離用戶最近的 Google 邊緣節點（Edge PoP），並在此處完成 TLS 終止；
- **階段二：Cloud Front 反向代理層**。此處執行三項關鍵檢查：第一是 Ingress Check，檢查來源 IP 是否符合規範（可設為 All Users、內部 VPC 或整合 Cloud Load Balancer 與 Cloud CDN）；第二是 IAM 身分鑑別，驗證是否有權限存取該服務；第三是 Traffic Split（流量切分），若開發者部署了多個版本（Revisions），可以在此設定金絲雀發布（Canary Deployment）的流量百分比；
- **階段三：Request Routing Layer（請求路由層）**。這是 Cloud Run 最核心的調度中樞。開發者可為服務設定每個實例的並發上限（Concurrency）。路由層會檢查現有實例是否有剩餘的 Slot（槽位）；若有，直接分配進 gVisor 沙盒容器中執行；若所有實例皆已滿載，請求會暫存於佇列（Queue）中，並立即通知 Auto Scaler 觸發快速擴容；
- **階段四：流量出站（Egress）**。支援 Direct VPC Egress，直接將目標子網 IP 分配給容器，讓容器直接與私有 VPC 資源低延遲互通。

**【學生報告者】**：很多同學會好奇：Cloud Run 到底是如何做到百毫秒級擴縮的？在底層架構上，Cloud Run 是基於開源的 **Knative Serving** 架構演進而來。在 Knative 中，主要由三個核心元件協同運作：
- 第一個是 **Activator**：當 Pod 數量縮容至零（Scale-to-Zero）時，Activator 負責暫存（Buffer）湧入的第一波請求，並立即向 Autoscaler 發出擴容訊號，徹底解決冷啟動（Cold Start）過程中的請求遺失問題；
- 第二個是 **Queue-Proxy**：以 Sidecar 模式與業務容器同駐在一個 Pod 中，隨時監控並回報容器內部的即時並發數與 QPS；
- 第三個是 **Autoscaler**：彙整來自 Activator 與 Queue-Proxy 的即時指標，精準計算出當前所需的副本數量。

**【學生報告者】**：特別值得一提的是，傳統 K8s HPA 是依據 CPU 或記憶體利用率來擴縮，這常常會引發嚴重的「系統顛簸（Thrashing / Flapping）」問題——例如 Java JVM 在啟動時 CPU 會短暫飆高，誤導系統過度擴容；而 Cloud Run 採用基於請求並發量（Request Concurrency）的 KPA 模型，並設計了「穩定視窗（Stable Window）」與「恐慌視窗（Panic Window）」雙機制，有效避免資源在容量邊界來回震盪。

**【學生報告者】**：接下來介紹我們的實作系統——「外送排單模擬系統」。外送平台是一個非常典型的潮汐流量場景，具有極為明顯的尖峰與離峰差異。

**【學生報告者】**：外送業務具有兩種截然不同的運算負載：第一種是「訂單派單」，在收到訂單的當下，系統需計算配送員分配與預估送達時間，屬於單次較重的運算；第二種是「配送追蹤」，在外送員前往目的地的過程中，系統每 2 秒必須重新執行一次 Dijkstra 最短路徑演算法來更新外送員位置與路況，屬於單次計算較輕但高頻反覆執行的負載。

**【學生報告者】**：在系統架構設計上，我們設立了兩組對照環境：
- **對照組（Dispatch Fix）**：固定容量版，最大實體數限制為 1 台（Max Instance = 1）；
- **實驗組（Dispatch Auto）**：自動擴充版，最大實體數可自動動態擴充至 20 台（Max Instance = 20）。

**【學生報告者】**：大家可能會問：為什麼架構中沒有接共享資料庫？我們特別強調：在實務上將資料存入 Redis 或 PostgreSQL 是標準做法，但在本次壓測實驗中，如果引入單一共享資料庫，在高並發尖峰時資料庫必然會率先成為效能瓶頸，從而掩蓋了固定版與自動擴充版在運算層的擴縮差異！為了保持「Max Instance」為全場唯一的控制變因，我們採用了「無狀態（Stateless）設計」，由客戶端在請求中自行攜帶配送狀態資料。

**【學生報告者】**：現在進入現場展示環節！請現場所有同學拿出手機，掃描螢幕上的 QR Code 進入我們的點餐系統。

**【學生報告者】**：大家進去後可以輸入自己的暱稱並隨便點一份餐，大家的名字就會即時顯示在投影幕上。

**【學生報告者】**：現在畫面上顯示的是「階段一：離峰階段」，目前只有全班同學在手動下單。左邊是固定版（1 台），右邊是自動擴充版（目前動態維持在 2 台）。因為目前請求量不大，兩邊都還能正常回應。大家可以看到畫面下方有外送員在即時移動，每 2 秒就會跑一次 Dijkstra 演算法計算最短路徑。

**【學生報告者】**：接下來進入「階段二：尖峰時段」！我們啟動另一台電腦的壓力測試腳本，模擬突發尖峰流量，每秒新增 30 位虛擬顧客持續發起下單與追蹤！大家現在請在手機上再次點餐下單！

**【學生報告者】**：大家看螢幕！壓測腳本一啟動，自動擴充版的機器數量瞬間從 2 台、6 台一路飆升，在短短 26 秒內迅速拉升到 18 台實例！大家在手機上點餐，右邊自動擴充版依然維持毫秒級的極速成功；但大家看左邊的固定版——請求開始瘋狂排隊，大量請求超過 10 秒直接噴出逾時錯誤（Timeout），成功率直線墜崖式崩跌！

**【學生報告者】**：我們切換到官方監控與實測數據圖表：在四分鐘的尖峰壓測中，固定容量版的平均成功率崩潰到只有 **9%**，平均回應時間拉長到 **3.6 秒**；而自動擴充版成功率維持在完美的 **100%**，平均回應時間始終維持在 **毫秒級**！在費用方面，透過 GCP 帳單分析可見，自動擴充版只有在流量湧入的幾分鐘內才產生實例計費，流量結束後迅速縮容，大幅降低營運成本。我們的報告到此結束，謝謝大家！

**【授課教師】**：好，非常精彩！大家再次給這組同學熱烈的掌聲！

**【授課教師】**：這組同學的實作非常用心，不僅概念講得清晰，最難得的是現場做了大規模的即時互動展示與壓力測試，後台數據與視覺化圖表做得相當具備業界水準。

**【授課教師】**：不過老師要給你們一個關鍵的架構與簡報建議：這也是後面幾組同學必須注意的。當你在向主管或技術客戶報告時，一定要從「聽眾的角度」來思考。你們今天把大量的技術細節放在前半段，直到第十三頁才講你們具體做了什麼。老師建議：應該在開場兩分鐘內就開門見山告訴大家「你們今天要做什麼核心驗證」，並先讓大家掃描 QR Code 體驗即時對比；當大家親眼目睹 1 台 vs. 18 台的崩潰與順暢差異後，大家帶著強烈的好奇心，你再回頭深入解釋背後 Google Cloud Run、Knative 與 Request-based 演算法的運作原理，這樣的說服力會更加震撼！

**【授課教師】**：另外，在架構選型上，如果時間充裕，你們應該多補充一頁：為什麼選擇 Google Cloud Run 而不是 AWS Lambda 或 ECS？它們在 Concurrency 支援度與冷啟動延遲上有什麼架構級別的差異？這能讓你們的技術深度更上一層樓。

**【授課教師】**：最後老師要補充一點：Auto Scaling 固然強大，但它並不是萬能的銀彈！在公有雲環境中，應對幾萬、幾十萬的 QPS，Cloud Run 能夠游刃有餘；但如果場景換成即將到來的阿里巴巴「雙十一」購物節，或者農曆春節鐵路搶票，那一秒鐘按下去是數千萬甚至上億次的並發請求！

**【授課教師】**：在這種極端吞吐量下，公有雲的通用自動擴充機制底層也會面臨物理伺服器調度極限。因此像阿里或大型跨國機構，必須自行研發專屬的「削峰填谷」架構，利用高效能分散式訊息佇列（RocketMQ / Kafka）、前置限流降級與記憶體快取技術，在封包到達運算層之前就先做多層次的流量洗滌，那又是另一門更高深的分散式架構學問了。
