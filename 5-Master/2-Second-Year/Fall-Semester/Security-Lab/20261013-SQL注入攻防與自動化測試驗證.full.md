## 🛡️ 課程開場與 SQL 注入核心概念介紹

**【授課教師】**：OK，好，有沒有人？好，這組同學請站好。我們換一個方式來介紹第三章，幫你們介紹一個實際上的範例，對，就是非常非常經典、非常典型的案例。好，辛苦了，繼續。我想再細一點第五章的介紹，好吧，開始。

**【游昇翰】**：大家好，我是游昇翰。那我們剛開完會，先歡迎大家一起往下看。那我們這組的報告主題是「從攻擊到防禦：SQL 注入（SQL Injection, SQLi）基礎」。那這是我們的目錄：我們首先先介紹什麼是 SQL 注入，接著我們會示範三種 SQL 注入攻擊技巧；在進行示範之後，我們會進行比較跟分析；後面我們會提出一些相對應的 SQL 注入防禦與實驗討論策略；最後在整份報告的結尾，我們整理了我們製作歷程作為參考心得分享。

**【游昇翰】**：那什麼是 SQL 注入呢？它的最核心概念是：因為系統對於 SQL 的組織結構，以及使用者輸入的資料之間的邊界過於模糊，導致惡意的攻擊者可以將惡意指令輸入進這種邊界之中，去造成我們資料表資料外洩，或者是取得相關資訊、推論有關我們資料表的敏感資訊。

**【游昇翰】**：在這個部分呢，我們有參考 2016 年的一篇論文，在這個論文裡面有提出各種不同種類的 SQL 注入攻擊形式。那我們把這一張表格整理出來，並且會一一來介紹。

**【游昇翰】**：首先是「恆真式攻擊（Tautology Attack）」。恆真式攻擊的核心概念是：將脆弱查詢條件改為恆真成立（例如 `' OR 1=1 --`），繼而去繞過我們的身分驗證頁面，或是取得資料表內的大量資料。

**【游昇翰】**：第二個地方比較特別的是「錯誤查詢注入（Illegal/Incorrectly Defined Queries / Error-based SQLi）」。這個部分呢，是我們的攻擊者可以輸入錯誤的 SQL 語法，讓我們的應用程式回傳資料庫錯誤頁面，攻擊者就可以根據這個錯誤頁面回傳的 Error Message，去推論我們資料表內的結構與相關敏感訊息。

**【游昇翰】**：第三個部分是「UNION 查詢注入（UNION Query Injection）」。在 UNION 查詢注入裡面呢，攻擊者會在 `UNION` 這個語法後面去合併一些自己想要執行的操作，去取得其他資料表的資訊。

**【游昇翰】**：第四個是「疊加查詢注入（Piggybacked Queries）」，也就是大家常說的批次打點式攻擊。這個攻擊的概念跟 UNION 很像，它往往是在原本查詢的結尾分號後面，加入一些額外的惡意操作。常見的操作可能是直接刪除某些資料表（如 `; DROP TABLE users;`），或者是竄改我們比較敏感的資料。

**【游昇翰】**：那下一個攻擊是「預存程序利用（Stored Procedures）」。什麼是預存程序呢？它的概念跟寫程式呼叫函式有點像。在資料庫開發初期，開發者就會先預寫好一些功能儲存在預存程序裡面，在後續執行時會比較方便。那每一種不同的資料庫，官方可能會提供一組標準的擴充預存程序（例如 MSSQL 的 `xp_cmdshell`）。如果惡意的攻擊者猜出我們的底層資料庫種類，他就可以針對預存程序的呼叫方式去設計對應的注入攻擊，甚至在資料庫主機上執行作業系統命令。

**【游昇翰】**：下一個是「推論型盲注（Inference / Blind SQLi）」。這個方法比較特別，它主要是透過應用程式的回應時間差（Time-based，例如注入 `WAITFOR DELAY`），或者是 True/False 兩種不同的頁面反應，去逐步推論我們資料表裡的字元資訊。這個技巧的使用情境，通常是在應用程式已經具備一定安全基礎、關閉了詳細錯誤回傳的情況下。因為攻擊者無法一步直接拿到資料，就只能逐步透過布林或時間差去猜解資料表裡的內容。

**【游昇翰】**：下一個是「自動化推論注入（Automated Inference）」。在這個攻擊方法中，它比較像是一種輔助技巧，核心概念是利用不同的編碼與混淆方式（Encoding / Obfuscation）去包裝我們的攻擊載荷（Payload），進而去規避 WAF、過濾規則或是應用程式的特徵偵測機制。

**【游昇翰】**：從第一種方法到自動化推論方法，都是早期經典論文所提出的。但隨著時代演變，現在已經是 2026 年，也有一些新興的攻擊方法衍生出來，最著名的就是「Prompt-to-SQL 自然語言生成 SQL 注入（LLM Prompt-to-SQL Injection）」。這主要是因為目前大型語言模型（LLM）廣泛應用在 Text-to-SQL 的轉譯系統中，攻擊者可以透過提示詞注入（Prompt Injection）來操控 LLM 產生惡意的 SQL 語句。

**【游昇翰】**：在我們後續的實驗之中，我們會主要針對三種經典技巧進行實作示範：第一種是恆真式攻擊去進行身分驗證繞過；第二種是 UNION 查詢注入；第三種是推論型盲注。我們會再來詳細解釋這三種攻擊技巧的實務原理。

## 💻 攻防靶場實驗環境部署與示範

**【游昇翰】**：首先，第一種恆真式攻擊是大家最熟悉的，關鍵 Payload 通常是使用 `' OR 1=1 --`，常見的應用場景就是繞過後台登入驗證頁面，或是撈取全部資料。第二種是 UNION 查詢注入，核心語法是利用 `UNION SELECT`，在 UNION 前面是開發者原本希望執行的合法查詢，而在 UNION 後面則是攻擊者自行拼裝的額外查詢。

**【游昇翰】**：所以攻擊者登入時，原本系統預設只希望展示 `account` 這個資料表，可是經過 UNION 查詢合併，攻擊者就有辦法跨表看到 `card_number` 甚至包含密碼欄位的敏感資料。

**【游昇翰】**：最後一個是推論型盲注（Inference）。它的邏輯比較複雜一點，我們會先準備兩段 SQL 測試條件，最大的差異是一個帶有 `AND 1=0`，另一個帶有 `AND 1=1`。`AND 1=0` 對應到的是 False 條件，而 `AND 1=1` 對應到的則是 True 條件。我們會先將 False 條件注入到應用程式裡面：如果應用程式本身有過濾防護，可能會回傳錯誤；但若應用程式存在漏洞，透過 True 與 False 回應狀態的細微差異，我們就能確定該注入點存在，進而逐字元盲測敏感資訊。

**【游昇翰】**：在開始深入實作前，我們有準備一個小遊戲讓大家體驗一下 CTF 的預選解題技巧。大家可以拿起手機或裝置，幫我掃描螢幕上的 QR Code。進去之後會是一個網頁，情境是：假設你們是情報員，目標是要獲取「每日訊報獨家密單」裡的機密資料。網頁裡面有題目與預設選項，大家要去思考選哪一個選項可以正確拿到機密資料。

**【游昇翰】**：好，大家幫我思考一下。有同學抽到了嗎？我看那邊好像有同學抽到了，你可以幫我舉手嗎？願意跟全班講一下你抽到的秘方是什麼嗎？好，OK，恭喜答對！這就是我們的小體驗，希望能幫助大家快速建立直觀理解。

**【游昇翰】**：接下來我們要介紹實際操作的靶場平台。我們使用的是國網中心（NCHC）提供的資安攻防檢驗平台（CDX / Cyber Range 平台），它讓使用者在一個安全受控的隔離環境下進行滲透測試與攻防演練。平台上提供了很多實戰範本，我們可以依據需求選擇靶機映像檔與網路架構。

**【游昇翰】**：在系統部署方面，我們使用單一虛擬機架構，並切分出攻擊機（Attacker VM）與靶機伺服器，透過虛擬內網進行隔離。接著我們會利用終端機與自動化腳本配合，進行三階段的滲透測試演練。

## 🔍 UNION 查詢注入與身分驗證繞過實作解析

**【游昇翰】**：在進行 UNION 查詢注入時，首先要解決的是「欄位數匹配」問題。因為 SQL 的 `UNION` 語法要求前後兩個查詢的欄位數量與資料型態必須完全一致，否則資料庫會直接拋出錯誤。

**【游昇翰】**：我們在靶機輸入欄位中測試注入指令。因為欄位數不對，資料庫立刻顯示紅色的查詢失敗訊息。為了避免浪費時間從一個欄位慢慢猜，我們最後測試輸入五個 `NULL`：`UNION SELECT NULL, NULL, NULL, NULL, NULL --`。貼上送出後，網頁成功回傳！這就代表原本後端開單查詢的 SQL 語法，底層正是回傳 5 個欄位。

**【游昇翰】**：確定了 5 個欄位數之後，我們就可以進行欄位映射。我們將 Payload 改為注入特定的敏感欄位：其中一個欄位對應到員工姓名 `displayName`，另一個欄位對應到員工內網帳號 `employeeName`，其餘三個欄位繼續用 NULL 補齊。送出之後，前端頁面原本顯示一般業務資訊的地方，直接印出了內部員工帳號清單（如海綿寶寶、小李、朱總等測試帳號）。

**【游昇翰】**：接著我們利用撈取出來的員工帳號進行下一階段的後台登入繞過。為什麼會產生登入繞過呢？因為後端程式直接採用了「字串拼接（String Concatenation）」：
```sql
SELECT * FROM users WHERE username = '$user_input' AND password = '$password_input'
```
程式把使用者在前端輸入的所有內容，未經轉義就直接拼進 SQL 語句之中。

**【游昇翰】**：攻擊者根本不需要知道正確密碼。只要在帳號欄位輸入 `' OR '1'='1` 或者 `' OR 1=1 --`，單引號 `'` 會先提前閉合掉原本 SQL 的字串常數，後面的 `OR 1=1` 讓判斷條件恆真，最後的 `-- `（Double Dash）則把後端剩下的 `AND password = ...` 比對邏輯全部註解掉！系統資料庫在執行時判定條件恆成立，攻擊者無須密碼便成功登入系統管理者後台。

## 🛡️ 企業端縱深防禦架構與參數化查詢

**【游昇翰】**：我們進一步分析這三種攻擊技巧的本質差異：
1. **恆真式攻擊（Tautology）**：利用邏輯恆真篡改身分驗證流程，直接達到權限繞過。
2. **UNION 查詢注入**：必須精確枚舉欄位數量與型態，透過合併查詢跨表竊取大量機密資料。
3. **推論型盲注（Inference）**：在無直接回顯與詳細報錯的環境下，透過多次條件測試（時間延遲或布林反應）逐字推導資料。

**【游昇翰】**：這些漏洞的共同根本原因，都是「外部使用者輸入未妥善處理，直接影響了 SQL 語法剖析樹（Parse Tree）的結構與執行邏輯」。針對這些威脅，我們整理了企業端防護策略，核心理念是建立「縱深防禦（Defense-in-Depth）」多層次控管：

**【游昇翰】**：最根本的核心防禦是「使用參數化查詢的預備語句（Prepared Statements with Parameterized Queries）」。
- 在傳統字串拼接中，SQL 語法與使用者輸入混在一起送入資料庫直譯器，輸入內容會直接改變語法結構。
- 而在參數化查詢中，資料庫會先對 SQL 查詢骨架進行預先編譯（Pre-compile），傳入的使用者資料只會被當成單純的參數值（Literal Value）處理，絕對不會被當成可執行的 SQL 代碼解析，從根本上杜絕了 SQL 注入的可能。

**【游昇翰】**：除了參數化查詢外，輔助的多層防護包括：
1. **輸入驗證與白名單過濾（Input Validation）**：在前端與後端對輸入格式、長度、字元型別進行嚴格檢核。
2. **最小權限原則（Principle of Least Privilege）**：資料庫連線帳號僅配置必要的最小權限（例如一般的登入查詢帳號絕不賦予 `DROP`、`ALTER` 或存取系統預存程序的權限）。
3. **錯誤與回應管理（Error Handling）**：關閉生產環境的詳細資料庫報錯回傳，前端僅顯示通用錯誤提示，將詳細堆疊追蹤資訊保留在伺服器內部 Log，阻斷 Error-based 盲注攻擊鏈。
4. **持續安全測試（Security Testing）**：將靜態代碼分析（SAST / Code Review）與動態黑箱滲透測試（DAST）納入 CI/CD 流程中持續檢驗。

**【游昇翰】**：最後分享我們的製作歷程。我們小組進行了兩次正式會議，充分參考老師的建議進行調整。在 AI 工具的使用上，我們主要用來協助概念理解、架構梳理、內容規劃與代碼除錯。最大的學習收穫是建立完整的攻防對抗思維，理解攻擊者如何尋找邊界漏洞，以及防禦者應如何在每個層次落實嚴謹控管。以上是我們的報告，謝謝大家！

## 🎓 授課教師講評：資料隱碼命名本質與代碼資料邊界哲學

**【授課教師】**：好，大家都看到剛才他們做的展示。我們花一點點時間來深入討論一下。這組同學講得很詳細、做得很用心。各位想一想，他們花很多時間做這個題目，最重要的核心意義在哪裡？

**【授課教師】**：各位知道為什麼在台灣的資安領域，二十年前大家會把「SQL Injection」翻譯成「資料隱碼攻擊」嗎？為什麼人家當初翻譯成中文的時候叫「資料隱碼」？

**【現場學員】**：因為正常來說資料只是用來查詢，但我們利用 SQL 指令去查詢時，把惡意指令藏在資料裡面，讓後端顯示出我們想要的資訊。

**【授課教師】**：很好！剛剛同學回答得很精準，這就是一開始游昇翰講的「邊界問題（Boundary Problem）」！

**【授課教師】**：一般人在網頁上看起來，你在輸入框裡打字，那些輸入進去的字對使用者來說是什麼？純粹是「資料（Data）」嘛！傳送資料、查詢資料。但是對於後端資料庫直譯器而言，因為程式碼寫得不嚴謹、用了字串拼接，你輸入的那些字直接跨越了邊界，在後端被當成了「指令/程式碼（Code）」來執行！

**【授課教師】**：人看到的是資料，但系統直譯引擎卻把它當成了「程式碼的主體」。這就是為什麼二十年前台灣前輩翻譯成「資料隱碼」——**把程式碼隱藏在資料欄位裡面**！

**【授課教師】**：不管是 Web 網站還是未來的智慧合約虛擬機（EVM），任何系統如果「資料與程式碼的邊界」劃分不清，攻擊者只要在資料欄位裡動手腳，後端的執行引擎就會被牽著鼻子走。這就是為什麼參數化查詢那麼重要，因為它從底層機制上強制將「程式碼骨架」與「純資料參數」徹底分離開來。

**【授課教師】**：這組同學的實作非常用心，將攻擊原理解釋得很透徹。希望大家回去之後多參考他們的投影片與靶場架構。時間差不多了，我們休息兩分鐘，下一節我們繼續把第十章的課程內容講完！
